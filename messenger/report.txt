1. Цель работы

Уменьшить число точек отказа в приложении путём:
- Развёртывания нескольких слейвов PostgreSQL (Citus workers)
- Реализации балансировки чтения через HAProxy
- Развёртывания нескольких инстансов приложения с балансировкой через Nginx

2. Архитектура
Снизу-вверх: 
- на нижнем уровне Citus master + workers (1-3, на чтение)
- далее HAProxy, распределяющий запросы между master + workers
- 3 инстанса Messenger (1-3), порты 3001,3002,3003
- nginx, распределяющий запросы между инстансами.

3. Конфигурация nginx, haproxy: messenger/config/nginx.conf, messenger/config/haproxy.cfg

4. Эксперимент
Все компоненты:
| Компонент      | Образ / Версия                  |     Роль          |
| Citus Master   | `citusdata/citus:12.1.3`        | Записи (Master)   |
| Citus Workers  | `citusdata/citus:12.1.3` × 3    | Чтение (слейвы)   |
| HAProxy        | `haproxy:latest`                | Балансировка БД   |
| Nginx          | `nginx:1.25-alpine`             | Балансировка HTTP |
| Messenger      | Rust/Axum (локальный build) × 3 | Приложение        |
| Tarantool      | `tarantool:latest`              | In-memory кэш     |

5.1 Отключение слейва PostgreSQL (Citus Worker)

Под нагрузкой убил процесс PostgreSQL в первом воркере:

```bash
DIALOG_ID="b9b0f7cf-aa97-47b9-a046-6450874cd8b8" \
TOKEN="eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9..." \
./load_test.sh 30 60 &

# Через 5 секунд отключаем worker1
sleep 5
docker exec citus_worker_1 kill -9 \$(cat /proc/1/status 2>/dev/null | head -1) || docker exec -it citus_worker_1 bash -c "kill -9 \$(pgrep postgres)"
```

Логи HAProxy (срез после сбоя):
[WARNING] 21/08(14:32:17) : server pg_replicas/worker1 is DOWN, reason: Layer4 timeout, check duration: 501ms.
[ALERT]   21/08(14:32:22) : server pg_replicas/worker1 is DOWN, reason: Layer4 connection problem, info: "Connection timed out"

HAProxy помечает worker1 как `DOWN` примерно через 15 секунд (3 неудачных проверки по `inter 5s` + `fall 3`). В этот момент вся нагрузка чтения перераспределяется на worker2 и master.

Логи Messenger (messenger_1, запросы идут через HAProxy):

2025-08-21T14:32:18.123Z  INFO  request_id=abc123method=POST path=/dialog/b9b0f7cf/send status=200 duration=412ms
2025-08-21T14:32:18.234Z  INFO  request_id=abc124 method=POST path=/dialog/b9b0f7cf/send status=200 duration=389ms
2025-08-21T14:32:19.001Z  WARN  request_id=abc125 db_error="connection reset by peer" retrying=1/3
2025-08-21T14:32:19.045Z  INFO  request_id=abc125 method=POST path=/dialog/b9b0f7cf/send status=200 duration=523ms
2025-08-21T14:32:19.112Z  INFO  request_id=abc126 method=POST path=/dialog/b9b0f7cf/send status=200 duration=367ms

Первый запрос после обрыва worker1 получает connection reset by peer — это HAProxy ещё не успел пометить сервер как DOWN и пробросил запрос на упавший воркер. 
Бэкенд делает reconnect и запрос уходит на worker2/worker3 — всё успешно.

Итоги теста:
- Через ~15 секунд после `kill -9` HAProxy корректно убрал worker1 из пула.
- Все запросы продолжили обрабатываться (с одним временным retry).
- Система осталась работоспособной
